## 의사결정 요약 (1페이지)

본 영역은 패스오더 플랫폼에 블로그 콘텐츠 자산을 신규 도입하여 1~2단계(인지·비교) 검색 의도 키워드를 흡수하고, 도메인 권위를 누적하며, 콘텐츠 본문을 인앱 전환의 톱-오브-퍼널로 활용하는 작업이다.

두 축으로 구성한다.

- **A. 발행 시스템** — 사내에서 이미 사용 중인 Notion을 작성 도구로 활용, 발행본은 S3 + CDN으로 서빙. 자체 에디터 없이 표준화된 1-click 발행 흐름 구축.
- **B. 키워드 발굴 프레임워크** — 외부 SEO 데이터와 패스오더 자체 데이터(앱 검색·주문·신규 입점)를 결합해 작성자가 "무엇을 쓸지 정하는 비용"을 줄임.

핵심 의사결정:

1. **A는 즉시 착수**한다. 마일스톤 7단계.
2. **B는 Phase 1(2~3주, 수동 검증)만 약속**한다. Phase 2 이후의 자동화는 Phase 1 결과를 보고 별도로 의사결정한다.
3. *"자동화는 검증된 패턴을 스케일링하는 도구이지, 패턴을 발견하는 도구가 아니다."* 본 원칙을 단계별 진행의 게이트로 둔다.

기대 효과 (6개월): 발행 콘텐츠 누적 100건+, 자연 검색 유입 MoM +15%, 콘텐츠 → 앱 진입률 5%+.

외부 비용 (Phase 1): 네이버 검색광고 API + 네이버 데이터랩 API (모두 무료). SerpAPI는 Phase 2 이후 도입 결정.

## A. 발행 시스템

### 핵심 의사결정 4가지

본 영역은 다음 4개 원칙 위에 설계되며, 이후 본문은 이 원칙의 *결과*만을 다룬다.

1. **본 서비스는 Notion API에 런타임 의존하지 않는다.** Notion은 작성/발행 워크플로우에서만 사용하고, 발행본의 진실은 S3에 둔다.
2. **모든 발행은 사람이 미리보기를 확인한 후 명시적으로 트리거한다.** 자동 발행 없음.
3. **미리보기와 운영 발행은 동일한 변환 파이프라인을 거친다.** 환경 차이로 인한 발행 사고를 차단.
4. **프리뷰 페이지는 사내 네트워크에서만 접근 가능하다.** 인덱싱 차단은 보조 안전장치이며, 1차 방어는 인프라 IP 제한이다.

### 작성 → 검수 → 발행 워크플로우

```
[Notion 작성] → [프리뷰 빌드] → [사내 미리보기 검수] → [FAB 클릭으로 발행] → [운영 페이지]
```

작성자는 사내 Notion DB에 글을 작성하고, 어드민에서 "프리뷰 빌드"를 실행한다. 발행 워커가 Notion 페이지를 가져와 MDX로 변환하고 이미지를 S3로 미러링한 뒤 미리보기 URL을 발급한다. 사내 네트워크에서 미리보기를 확인한 작성자(또는 검수자)가 우하단 FAB 버튼으로 발행을 트리거하면, 발행 API가 미리보기를 운영 경로로 복사하고 인덱스를 갱신한 뒤 CDN 캐시를 무효화한다. 운영 URL로 자동 리디렉션된다.

작성 컨벤션, 커스텀 컴포넌트 신택스, 이미지/캐시/접근 제어 정책의 상세는 **부록 1**을 참조.

### 페이지 구성

| 경로 | 용도 | 접근 제어 |
| --- | --- | --- |
| `/blog/{slug}` | 운영 발행본 | 공개 |
| `/blog` | 운영 발행본 목록 | 공개 |
| `/preview/{slug}` | 미리보기 (FAB로 발행) | 사내 네트워크 한정 |

운영/프리뷰는 동일한 `PostView` 컴포넌트를 사용하며 데이터 소스만 다르다. 프리뷰 페이지는 상단에 "미리보기 모드" 배너와 빌드 시각을 노출하고 메타에 `noindex / nofollow`를 적용한다.

### 마일스톤

| 단계 | 내용 |
| --- | --- |
| 1 | 발행 워커 (Notion → MDX 변환, S3 업로드, 이미지 미러링) |
| 2 | 커스텀 컴포넌트 1~2종 (StoreCard 등) |
| 3 | 프리뷰 / 운영 페이지 렌더링 |
| 4 | 인프라 IP 제한 적용 (WAF / ALB) |
| 5 | FAB 발행 기능 + 발행 API |
| 6 | CDN 무효화 + 인덱스 자동 갱신 |
| 7 | 모니터링 / Slack 알림 / 감사 로그 |

### 추후 검토

다국어 슬러그 구조(`posts/{locale}/{slug}/*`), 예약 발행, 발행 후 롤백(S3 버저닝 활용), 댓글/좋아요 등 사용자 인터랙션, RSS / 사이트맵 자동 생성(S2 ② Sitemap 최적화와 연계).

## B. 키워드 발굴 프레임워크

### 콘셉트와 차별화

일반 SEO 도구는 검색량/경쟁도/트렌드만 본다. 본 도구는 여기에 **외부 도구가 절대 볼 수 없는 패스오더 자체 데이터**(앱 내 검색어, 매장별 주문량, 신규 입점, 지역·시간대별 행동)를 결합한다. 외부 트렌드보다 1~2주 앞서 시즌 키워드를 잡거나, "성수동 출근길 인기 메뉴"처럼 외부에서 만들 수 없는 콘텐츠 소재를 발굴할 수 있다는 게 본 도구의 차별점이다.

비목표:

- Ahrefs/Semrush 같은 종합 SEO 도구의 전면 대체.
- 백링크/도메인 권위 점수의 자체 산출.
- AI 콘텐츠 자동 생성 — 별도 초안 도구 영역.

### 검색 의도 단계별 키워드 매핑

키워드를 검색량이 아니라 **의도 단계**로 분류해 콘텐츠 깔때기를 구성한다.

| 단계 | 의도 | 역할 | 예시 |
| --- | --- | --- | --- |
| 1단계 | 인지 / 정보 탐색 | 트래픽 유입 | "여름 시즌 한정 음료 추천" |
| 2단계 | 비교 / 대안 검토 | 신뢰 형성 | "성수동 노트북 작업 카페" |
| 3단계 | 결정 / 구매 임박 | 전환 유도 | "성수 ○○카페 웨이팅" |
| 4단계 | 행동 / 즉시 주문 | 본문 내 전환 장치 | "줄 안 서는 카페 앱" |

블로그 콘텐츠의 주력은 1~2단계이며, 4단계 키워드는 별도 콘텐츠가 아닌 1~2단계 콘텐츠 본문 안에 전환 장치로 녹인다.

### 점수 모델 (PVS) — Phase 1 단순화 버전

원안의 PVS는 6개 항목을 가중치로 결합했으나, 그중 절반(의도 적합도 / 전환 연관성 / 시의성)은 사람의 라벨링 없이 신뢰성 있게 자동 산출하기 어렵다. Phase 1에서는 다음 3개 항목으로 축소한다.

| 항목 | 산출 방식 | 가중치 |
| --- | --- | --- |
| 검색량 점수 | log(월간 검색량) 정규화 | 0.40 |
| 경쟁 진입가능성 | 상위 10개 결과 도메인 권위 평균의 역수 | 0.30 |
| 자체데이터 우위 | 패스오더 데이터로만 답할 수 있는 정도 (담당자 라벨, 0~100) | 0.30 |

가중치는 Phase 1 발행 결과로 검증/보정한다. 자동 보정 로직은 Phase 4 이후 검토 사항.

**Goodhart's law 방지**: 작성자에게 점수는 정렬 도구일 뿐이며, 최종 발행 판단권은 사람에게 있다. 점수를 추격하는 콘텐츠 양산을 막기 위해 Phase 1 동안 작성자의 거부 사유를 모두 누적해 모델 회고에 사용한다.

### Phase 1 — 모델 검증 (2~3주)

목표: 점수 모델이 실제로 좋은 키워드를 추천하는지, 그리고 그 추천을 따라 발행한 콘텐츠가 예상 트래픽을 만들어내는지 검증한다.

진행:

- 시드 키워드 100개 수동 등록 (지역명 / 조건어 / 메뉴명 카테고리)
- 외부: 네이버 검색광고 API(무료) + 네이버 데이터랩 API(무료)
- 내부: 분석 DB의 앱 검색 / 주문 / 신규 입점 — *운영 DB 직접 쿼리 금지*
- 점수 산출 → 구글 시트 출력
- TOP 10 중 5~10건 직접 발행 → 4주 트래픽 추적

**SerpAPI는 Phase 1에서 도입하지 않는다.** 가장 비싼 외부 의존이면서 초기 검증에는 가장 덜 본질적이다. 네이버 데이터만으로 모델이 작동함이 입증된 후 도입을 검토한다.

Phase 1 운영 가이드(시드 카테고리, 데이터 검증 체크, 시트 구성, 발행 후 회고 양식)는 **부록 2**.

### Phase 2 진입 게이트 (명시적 의사결정 포인트)

Phase 1 종료 시점에 다음 기준을 충족해야 Phase 2(자동화) 진입을 결정한다. 충족하지 못하면 모델 자체를 다시 설계한다.

1. 발행한 5~10건 중 **70% 이상이 발행 4주 후 예상 트래픽 범위(±50%) 안에 들어왔는가**.
2. 작성자가 추천 TOP 10 중 채택한 비율이 **50% 이상**인가.
3. 거부된 추천의 거부 사유가 **모델로 학습 가능한 패턴**(특정 카테고리 약점 등)으로 분류되는가.

게이트 통과 시 Phase 2를 결정하되, 그 형태는 **Airflow DAG가 아니라 재현 가능한 SQL + 주간 시트 자동 갱신**으로 시작한다. 분석가가 매주 30분에 운영하는 형태가 안정적으로 3개월 이상 돌아간 후 DAG화를 재검토한다.

### Phase 3~4 (유보)

원안의 Phase 3(운영 안정화), Phase 4(학습 기반 가중치 보정)는 본 v0.2에서 약속하지 않는다. Phase 2가 검증된 시점의 별도 기획서로 분리한다. 자동화 인프라(Airflow DAG, Slack 인터랙티브, 대시보드)는 모두 그 시점의 결정 사항이다.

### KPI

도구 자체:

- Phase 1 추천 채택률 50%+
- 발행 5~10건 중 트래픽 예측 적중률 70%+

비즈니스 (도구가 기여, 6개월):

- 발행 콘텐츠 100건+
- 자연 검색 유입 MoM +15%
- 콘텐츠 → 앱 진입률 5%+

### 추후 검토

가중치 자동 보정 로직(발행 데이터 누적 후), 시드 키워드 자동 확장(자동완성/연관검색어), SerpAPI 도입 시점 및 비용 모니터링, 갱신 후보 자동 분류(기존 글 중 순위 하락 / 정보 노후).

## 결론 — 두 축의 결합

본 영역의 종착 모델은 **"무엇을 쓸지(B)"와 "어떻게 발행할지(A)"의 결합**이다. B가 매주 작성 큐를 채우고, 작성자는 Notion에서 글만 쓰며, A가 프리뷰 → 검수 → 발행을 표준화된 1-click 흐름으로 처리하는 형태다.

다만 본 v0.2는 그 종착 모델을 한 번에 약속하지 않는다. **A는 검증된 표준 작업이므로 즉시 착수하되, B의 자동화는 Phase 1 검증을 통과한 다음에만 다음 단계로 넘어간다.** 자동화를 늦추는 만큼 초기 투입 리소스가 줄고, 모델이 틀렸을 때의 매몰 비용도 줄어든다.

## 의사결정 요약 (1페이지)

매장 상세의 메뉴 클릭은 충분히 발생하지만(GA4/Snowflake 기준), 클릭 시 단순 인앱 전환 다이얼로그만 노출되어 인앱 전환율이 베이스라인 0.67%(S1 측정)에 머무는 상태다. 본 영역은 매장 상세 UX를 개편하고 메뉴판 + 장바구니 기능을 신규 구축하여, 유저가 "메뉴 조립 → 주문 직전"까지 웹에서 진행한 뒤 cart 상태를 그대로 인앱으로 전달하는 동선을 만든다.

네 축으로 구성한다.

1. **매장 상세 UX 개편** — 탭 → 단일 스크롤 영역 구성. 사용성 + SEO 효과
2. **매장 메뉴판 페이지 신규** — `{매장+메뉴}` 키워드 흡수용 단독 색인 페이지
3. **장바구니 시스템 구축** — 게스트 cart API + LocalStorage + 카카오싱크 매핑
4. **장바구니 → 인앱 전환 이탈 방지** — "설치 게이트 통과율" 향상에 집중

핵심 의사결정:

1. **매장 상세는 수직 배치로 전환한다.** 사용성과 모바일 우선 색인 환경의 SEO 효과를 동시에 노린다.
2. **게스트 cart API를 신규 구축**한다. 첫 메뉴 담김 시점에 cart_id를 발급해 LocalStorage + 쿠키에 저장.
3. **카카오싱크 트리거를 헤더 "100원 이벤트" → "장바구니 담기" 시점으로 이동한다.** 본 영역의 설치 게이트 통과율을 결정짓는 단일 변경. 운영/CS/약관 협의 선결.
4. **인앱 전환 모달은 2단계 분리**(요약 + 메리트 → 설치 안내)로 마찰을 완화하고 A/B로 검증한다.
5. **기술적 cart 손실은 OneLink + 게스트 cart API로 이미 봉쇄됨.** 본 영역의 진짜 과제는 *"장바구니까지 담았으나 앱을 설치하지 않고 이탈하는 유저"*를 어떻게 회수할 것인가다.

기대 효과: 매장 상세 → 인앱 전환율 베이스라인(0.67%) 대비 향상(목표는 측정 후 베이스라인 재설정), `{매장+메뉴}` long-tail 흡수, 매장 페이지의 토픽 권위 강화, S2 ② Sitemap 최적화 효과 결합.

## 1. 매장 상세 페이지 UX 개편

### AS-IS / TO-BE

AS-IS는 메뉴 / 소식 / 스토리의 3개 탭. TO-BE는 단일 스크롤의 영역 단위 구성으로 전환한다.

| 영역 | 뷰 형태 | 구성 |
| --- | --- | --- |
| 인기 메뉴 | 세로 리스트 | 자동 산출 N개 + 메뉴판 전체보기 CTA |
| 소식 | 가로 스크롤 | 진행중/예정 이벤트 카드 (S1 매장 소식 컴포넌트 재사용) |
| 스토리 | 가로 스크롤 | 매장 스토리 카드 3개 + 다른 매장 스토리 보기 |

### 사용성 사유

탭 depth 제거로 콘텐츠 도달률이 상승한다(S1에서 적립마켓을 탭이 아닌 배너 영역으로 처리한 것과 동일 원칙). 메뉴/소식/스토리가 단일 스크롤에서 동시에 노출되어 매장의 종합적 가치를 한 화면에서 인지할 수 있고, 가로/세로 뷰 차별화로 인기 메뉴(주력 전환 영역)에 시선이 집중된다.

**탭 클릭, 스크롤에 대한 각각 로그 확인하여 탭 대비 스크롤 액션이 유리하다는 내용 추가**

### SEO 사유 (신규 — v0.1에 누락)

수직 배치는 모바일 우선 색인 환경에서 다음 효과를 만든다.

1. **Hidden content 가중치 감점 회피** — 탭의 비활성 콘텐츠는 모바일 색인에서 가중치가 낮아진다. 수직 배치는 이 감점이 발생하지 않는다.
2. **토픽 시그널 강화** — 매장 페이지가 메뉴(`hasMenu`) + 이벤트(`Event`) + 스토리(`Article`)가 결합된 단일 entity 페이지로 인식된다. `{매장명} {보조 키워드}` long-tail 흡수.
3. **내부 링크 깊이 단축** — 매장상세 본문에서 메뉴판 페이지로 깊이 1 직링크. S2 ② Sitemap 최적화의 효과를 받침.
4. **Schema markup 명시성 강화** — 가시 콘텐츠와 schema가 1:1 대응. Rich Result(메뉴 스니펫, 이벤트 스니펫) 노출 가능성 증가.
5. **Anchor link 기반 jump-to-section** — 영역별 anchor(`#menu`, `#news`, `#story`) 부여로 검색 결과의 "해당 섹션으로 이동" 노출 가능성 확보.

CWV 영향 관리, 카니발리제이션 회피, 빈 영역 처리, 기존 탭 URL 301 redirect 등 SEO 이행 체크리스트는 부록 2 참조.

### 인기 메뉴 자동 산출 정책

분석 DB의 최근 30일 주문량 상위 N개(활성 메뉴 한정)를 기본으로 한다. 인기 메뉴 0건 매장은 "이 매장의 메뉴" 폴백(메뉴 등록 순)으로 대체. 정렬·가산 정책(주문량 / 주문 비중 / 신규 메뉴 가산점)은 후속 결정.

## 2. 매장 메뉴판 페이지 신규 구축

매장상세의 인기 메뉴/메뉴판 CTA, 검색 유입, 외부 링크 모두에서 진입할 수 있는 **`{매장+메뉴}` 키워드 흡수용 단독 색인 페이지**를 신규 구축한다.

### URL 구조

| 페이지 | 경로 | 색인 정책 |
| --- | --- | --- |
| 매장 메뉴판 | `/store/{storeId}/menu` | **색인 대상**, sitemap 자동 적재 (S2 ②와 통합) |
| 메뉴 다이얼로그 활성 | `/store/{storeId}/menu/{menuId}` | SSR 렌더, canonical은 메뉴판 본문으로 통일 |

메뉴 다이얼로그 URL을 별도 색인할지 canonical로 통일할지는 후속 결정 사항. 초기에는 통일 권장(색인 분산 회피).

### 페이지 구성

상단부터 매장 요약(이름·평점·영업상태·뒤로가기) → 카테고리 네비게이션(스티키 헤더, 카테고리 점프) → 카테고리 그룹핑된 메뉴 리스트 → 하단 고정 장바구니 바(수량/합계/주문하기).

메뉴 클릭 시 다이얼로그가 활성화되어 메뉴 이미지·설명·가격, 옵션 선택(필수/선택), 수량 조절, "장바구니 담기" 버튼이 노출된다. 장바구니 영역은 하단 고정 바 + 펼침 시 상세이며, 메뉴별 옵션·수량 조정과 개별 삭제, "주문하기" 버튼(인앱 전환 트리거)을 포함한다.

### 진입 시나리오

| 진입 경로 | 동작 |
| --- | --- |
| 매장상세 인기 메뉴 카드 클릭 | 메뉴판 페이지 + 해당 메뉴 다이얼로그 자동 활성 |
| 매장상세 "메뉴판 전체보기" CTA | 메뉴판 페이지 (첫 카테고리) |
| 검색 결과 / 외부 링크 | 메뉴판 페이지 직접 진입 |

### S1 키워드 분석과의 직접 연결

S1 분석에서 노출 대비 클릭이 저조했던 키워드 다수가 `{매장+메뉴}` 패턴이었다. 메뉴판 페이지 신설은 이 수요를 직접 흡수하기 위한 SEO 자산이다.

| 키워드 | 노출 | 클릭 | CTR | 흡수 가능성 |
| --- | --- | --- | --- | --- |
| 하삼동커피 메뉴 | 1,038 | 0 | 0% | ★★★★★ |
| 백억커피 메뉴 | 3,550 | 28 | 0.8% | ★★★★★ |
| 텐퍼센트 메뉴 | 92 | 38 | 0.3% | ★★★★ |
| 더치앤빈 메뉴 | 181 | 8 | 4.4% | ★★★ |

### Schema / 메타데이터

`Restaurant.hasMenu` → `Menu` → `MenuSection` → `MenuItem` 트리를 노출하고, `MenuItem`에는 `name`, `description`, `image`, `offers.price`, (가능 시) `suitableForDiet`을 권장 속성으로 채운다. 페이지 메타는 `<title>` = `{매장명} 메뉴판 | 패스오더`, `<meta description>` = 매장 인기 메뉴 N개 + 가격대 + 매장 위치 요약(S1 메타 중복 1.1만건 해소 정책과 동일 룰). 매장상세 ↔ 메뉴판 ↔ 메뉴 다이얼로그 간 내부링크 정합성과 `breadcrumb` schema도 함께 노출한다.

## 3. 장바구니 시스템

### 게스트 장바구니 API

본 영역에서 신규 구축. cart 상태를 서버에 보존해 인앱 전환 / 재방문 / 디바이스 간 이동을 모두 지원한다.

| 작업 | 시점 | 효과 |
| --- | --- | --- |
| cart 생성 | 첫 메뉴 담김 | cart_id 발급, LocalStorage + 쿠키 저장 |
| cart 동기화 | 메뉴 추가/삭제/옵션 변경 | 서버 상태와 일치 유지 |
| cart 조회 | 페이지 재방문, 인앱 진입 | LocalStorage cart_id로 복원 |

### 상태 보존 정책

| 상태 | 보존 기간 |
| --- | --- |
| 익명 cart_id (LocalStorage / 서버) | 7일 |
| 카카오싱크 매핑된 cart | 30일 |
| 설치 미완료 유저용 알림톡 발송 윈도우 | 24~48시간 (운영 정책 협의 필요) |

## 4. 장바구니 → 인앱 전환 이탈 방지

### 운영 전제 (이미 확보된 기술 흐름)

- **OneLink(AppsFlyer 원링크)** 딥링크가 이미 운영 중. 설치/미설치 분기, 설치 후 첫 실행 시점까지 cart_id 등 파라미터 전달 채널 확보됨.
- **게스트 장바구니 API**가 본 영역에서 신규 추가됨. cart 상태의 서버 보존 확보됨.

따라서 본 영역에서 해결해야 할 진짜 과제는 cart 상태의 손실이 아니라:

> **"장바구니까지 담았으나 앱을 설치하지 않고 이탈하는 유저"를 어떻게 설치 → 인앱 전환까지 끌고 갈 것인가**
> 

이다(= shopping cart abandonment **at the install gate**). 기술 흐름은 OneLink + 신규 API로 이미 닫혀 있고, 개선 여지는 **"OneLink → 앱스토어 → 설치" 게이트의 통과율**을 끌어올리는 데 집중된다.

### 핵심 과제 1 — 설치의 가치를 즉시 가시화 (Pre-install nurturing)

"주문하기" 클릭 직후 노출되는 인앱 전환 화면에서 유저가 *"왜 지금 설치해야 하는가"* 를 즉시 인지하도록 구성한다. Cart 요약(매장명·메뉴명·옵션·합계)을 노출해 결제 흐름의 시각적 연속성을 만들고, "앱 설치 후에도 담은 메뉴는 그대로 유지돼요" 카피로 단절감을 완화한다. 설치 보상(첫 주문 할인, 적립금 등), 설치 시간 기대치("30초면 설치 완료"), 신뢰 신호(누적 이용자 수, 후기, 평점)를 함께 노출한다. 목적은 앱 설치를 결제 흐름의 *외부 비용*이 아닌 *내부 단계*로 느껴지게 만드는 것.

### 핵심 과제 2 — 카카오싱크 트리거 시점 이동 (가장 중요한 회수 채널)

설치하지 않은 유저를 추후 따라잡을 수 있는 사실상 유일한 경로는 **카카오싱크 동의 후의 알림톡/카카오 메시지**다. 동의를 받는 시점이 본 영역의 효과를 결정한다.

| 구분 | 시점 | 한계 / 효과 |
| --- | --- | --- |
| AS-IS | 상단 헤더 "100원 이벤트" 진입 | 의향이 약한 유저까지 포함, cart 발생 유저는 누락 가능 |
| TO-BE | **"장바구니 담기" 시점** (첫 메뉴 담김 직후, 비강제) | cart 가치가 발생한 시점에 정확히 동의 받음 |

싱크 완료 시 효과는 세 가지다. 사용자 식별자 ↔ cart_id 매핑으로 **인앱 자동 로그인 + cart 복원**이 가능해지고, "주문하기" → 인앱 전환에서 **추가 인증 단계가 제거**된다. 그리고 **싱크는 했으나 앱 설치 안 한 유저까지 알림톡으로 회수 가능**해진다. 이 단일 변경이 본 영역 설치 게이트 통과율을 가장 강하게 결정짓는다. 운영/CS/약관 협의가 우선되어야 한다.

### 핵심 과제 3 — 인앱 전환 모달의 2단계 분리 (마찰 완화)

"주문하기 → 즉시 앱스토어"가 아닌, 의사결정 단계를 둘로 분리한다.

```
[Step 1] 주문 요약 + 설치 메리트 노출
  ├ Cart 요약 (이미지 포함)
  ├ "앱 설치 시 받는 혜택" 명시
  └ [앱 설치하고 결제] / [닫기]

[Step 2] 설치 후 자동 복원 안내
  ├ "설치 후 앱을 실행하면 담은 메뉴가 그대로 보여요"
  └ OneLink → 앱스토어
```

A/B 테스팅으로 **2단계 분리 vs 즉시 OneLink 진입** 효과를 검증한다.

### 핵심 과제 4 — 설치 거부/보류 유저 회수 경로

설치 게이트를 즉시 통과하지 않은 유저도 cart을 잃지 않고 추후 회수될 수 있도록 한다.

| 상황 | 회수 동작 |
| --- | --- |
| 인앱 전환 모달 닫고 메뉴판으로 복귀 | LocalStorage cart_id 유지, 페이지 재방문 시 cart 자동 표시 |
| "나중에 설치" 의사 | cart 링크를 카카오톡으로 보내기 / 즐겨찾기 안내 |
| 카카오싱크 완료 + 미설치 유저 | 운영 동의 범위 내 알림톡 발송 (예: "{메뉴} 담아두셨어요. 지금 앱 설치하면 N% 할인") |
| PC 사용자 (설치 자체가 어려움) | cart 정보를 담은 QR 코드 발급 → 모바일 OneLink로 이어붙이기 |

### 설치 게이트 측정 퍼널 (신규)

기존 8단계 전환 퍼널 위에 "설치 게이트" 구간만 분리해 별도 추적한다.

| 단계 | 정의 |
| --- | --- |
| A | 주문하기 클릭 (전체) |
| B | OneLink 진입 (앱스토어 또는 인앱) |
| C | 앱 설치 완료 (미설치 유저 한정) |
| D | 인앱 첫 실행 + cart 복원 성공 |
| E | 인앱 주문 완료 |

핵심 지표:

- **설치 게이트 통과율** = C / (A 中 미설치 유저)
- **복원 성공률** = D / C
- **설치 게이트 → 주문 완료** = E / A
- **카카오싱크 적용 코호트 vs 비싱크 코호트 비교** — 카카오싱크 트리거 이동의 효과 검증

## 결론 — 4축의 결합

본 영역의 핵심은 **웹에서 cart까지 조립한 유저를 인앱으로 이어 결제까지 도달시키는 것**이다. 그 흐름에서 매장 상세 UX 개편(축 1)이 콘텐츠 도달률과 SEO 토픽 시그널을 만들고, 메뉴판 페이지 신규(축 2)가 `{매장+메뉴}` 키워드를 흡수해 새로운 트래픽 진입로를 열며, 장바구니 시스템(축 3)이 cart 상태의 서버 보존을 보장하고, 인앱 전환 이탈 방지 설계(축 4)가 cart을 가진 유저를 설치 → 인앱까지 끌고 간다.

기술 흐름은 이미 닫혀 있다(OneLink + 게스트 cart API). **본 영역의 비즈니스 효과는 "카카오싱크 트리거 시점 이동"이라는 단일 운영 결정과 인앱 전환 모달의 디자인 결정에 가장 강하게 좌우된다.**

## 부록 2 — SEO 이행 체크리스트 (수직 배치 변경)

수직 배치 전환 시 SEO 효과를 누리려면 다음 항목이 함께 이행되어야 한다.

### Core Web Vitals 영향 관리

- 인기 메뉴는 첫 화면에 보일 N개만 priority load (`fetchpriority="high"`, `<link rel="preload">`).
- 소식/스토리 가로 스크롤 영역은 lazy-load.
- 이미지 webp + 1600px 리사이즈 (블로그 발행 시스템 정책과 동일 룰).

### 카니발리제이션 방지 (매장 상세 ↔ 메뉴판)

- 매장 상세는 인기 메뉴 N개 + 폴백까지만, 메뉴판은 전체 메뉴 + 카테고리/옵션/가격까지로 의도/depth 차별화.
- 매장 상세 → 메뉴판 anchor text는 "메뉴판 전체보기"로 통일.
- 두 페이지 모두 self-canonical.

### 빈 영역 / Thin content 처리

- 소식 0건, 스토리 0건 영역은 자동 hide.
- 인기 메뉴 0건 → "이 매장의 메뉴" 폴백.

### 기존 탭 URL 처리

- Search Console에서 `?tab=*` 파라미터 색인 현황 사전 확인.
- 색인된 URL은 단일 매장 상세 URL로 **301 redirect** (검색 의도 + 링크 자산 보존).

### Anchor 영역 / jump-to-section 노출

- `#menu`, `#news`, `#story` 부여.
- `WebPageElement` schema로 영역 명시 (검색 결과의 "해당 섹션으로 이동" 노출 가능성 확보).

## 부록 3 — 측정 설계

### 전환 퍼널 (신규 8단계)

| 단계 | 측정 위치 | 비고 |
| --- | --- | --- |
| ① 매장상세 진입 | GA4, Snowflake | 베이스라인 |
| ② 인기 메뉴 클릭 | GA4 이벤트 | 신규 |
| ③ 메뉴판 페이지 진입 | GA4 페이지뷰 | 신규 |
| ④ 메뉴 다이얼로그 노출 | GA4 이벤트 | 신규 |
| ⑤ 장바구니 담기 (cart_id 발급) | 서버 + GA4 | 신규 |
| ⑥ 주문하기 클릭 | 서버 + GA4 | 신규 |
| ⑦ 인앱 cart 복원 성공 | 인앱 SDK 이벤트 | 신규 |
| ⑧ 주문 완료 | 인앱 SDK 이벤트 | 최종 KPI |

### Snowflake 대시보드 신규 항목

- 단계별 전환율 (매장별 / 카테고리별 / 디바이스별)
- 인앱 미설치 → 설치 → cart 복원 성공률 (Deferred Deep Link 효과 측정)
- 메뉴별 장바구니 진입률 / 주문 전환율
- cart 미주문 이탈 패턴 (담은 후 X분 내 미주문 비율 등)

### Search Console 비교 (수직 배치 배포 전후 4주씩)

- 매장 상세 URL의 평균 노출수 / CTR / Position
- `{매장명} {보조 키워드}` long-tail 노출 키워드 수
- 매장 상세 페이지 모바일 LCP 75p (악화 방지 모니터링)

### A/B 테스팅 후보

| 영역 | A | B | 측정 |
| --- | --- | --- | --- |
| 인기 메뉴 노출 개수 | 3개 | 5개 | 메뉴 클릭률, 메뉴판 진입률 |
| 장바구니 바 카피 | "주문하기" | "앱에서 결제하기" | 클릭률, 복원 성공률 |
| 카카오싱크 트리거 시점 | 장바구니 담기 | 주문하기 클릭 | 싱크 동의율, 인앱 전환율 |
| 인앱 진입 후 동작 | cart 복원 후 매장 페이지 | cart 복원 후 결제 페이지 자동 진입 | 주문 완료율 |

### 리마인드 시나리오 (운영 정책 협의 후 단계적 도입)

| 트리거 | 채널 | 카피 예시 |
| --- | --- | --- |
| 카카오싱크 + 주문하기 클릭 + 30분 미설치 | 알림톡 | "{매장명}에서 {메뉴}를 담아두셨어요. 지금 앱 설치하면 N% 할인!" |
| 카카오싱크 + cart 7일 만료 임박 | 알림톡 | "담아두신 메뉴가 곧 사라져요. 한 번 더 확인해 보세요" |
| 비싱크 + 재방문 | 웹 | LocalStorage cart 자동 복원 + 인앱 전환 CTA 재노출 |

## 부록 5 — 추후 검토 사항

- **영업시간/판매 가능 시점**: 메뉴별 판매 가능 시간(브레이크 타임 등) 매핑, 매장 휴무 시 장바구니 동작 정책
- **옵션 복잡도**: 필수/선택 옵션 그룹 처리, 옵션 가격 가산 규칙
- **장바구니 머지 정책**: 비회원 cart_id ↔ 카카오싱크 후 회원 cart 머지 (충돌 시 우선순위 결정)
- **재고/품절**: 메뉴 품절 시 다이얼로그·장바구니 처리 (자동 제거 vs 알림)
- **가격 변동**: 웹 담은 시점 ↔ 인앱 진입 시점 사이 가격 변동 시 정책
- **다매장 장바구니 정책**: 1 cart = 1 매장 원칙 유지 여부, 타 매장 메뉴 추가 시 안내 UX
- **메뉴 다이얼로그 URL 색인 정책**: 색인 허용 vs canonical 통일
- **인앱 진입 후 결제 자동 진입 vs 사용자 확인 후 진입**: A/B 결과에 따라 결정
- **PC 사용자 cart 이전 UX**: cart QR 코드 발급 시 만료·보안 정책, 카카오 메시지로 cart 링크 발송 옵션
- **알림톡 리마인드 운영 정책**: 발송 윈도우, 빈도 상한, 동의 범위, 카피 표준화 — 운영/CS/약관 협의 필요
